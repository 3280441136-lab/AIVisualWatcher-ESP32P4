## 项目总目标

做一个单方向三模态行人入侵检测装置，先完成功能闭环，再考虑低功耗和更复杂的联网协议。

第一版功能闭环：

```text
雷达触发
    -> PIR 二次确认
    -> 摄像头采图
    -> 边缘 AI 行人检测
    -> 本地报警或状态提示
    -> Wi-Fi 上传事件和 JPEG 图片
```

当前约定：

- 本地报警需求保留，但蜂鸣器/LED 的型号、GPIO 和驱动方式还没有确认。
- 先不急着写报警组件。
- 必须等视觉 AI 确认“是人”以后，才允许后续报警或点亮提示。
- 低功耗、MQTT、远程推送、参数下发、在线状态管理、LP Core / HP Core 唤醒优化、夜间效果优化都放到第二版。

当前代码结构：

- `components/pir`：配置 PIR GPIO 输入，提供 `pir_is_active()` 读取当前电平。
- `components/vision`：已经创建为独立组件，公开 `vision_init()` 和 `vision_set_ai_enabled()`；当前 `vision_init()` 初始化 JD9365 DSI 屏幕、OV5647 -> CSI -> ISP 摄像头链路、PPA 显示合成任务和 ESP-DL 行人检测模型，`vision_set_ai_enabled()` 由状态机控制 AI 后台任务启停。
- `managed_components/waveshare__esp_lcd_jd9365_10_1`：通过 IDF Component Manager 引入的微雪 JD9365 10.1 寸屏幕组件。

## 当前状态机

当前源码里的状态机是最小可学习版本：

```text
STATE_WAIT_RADAR
    -> STATE_CHECK_PIR
    -> STATE_CHECK_VISION
    -> STATE_COOLDOWN
    -> STATE_WAIT_RADAR
```

早期需求文档里出现过 `STATE_ALARM`、`STATE_UPLOAD`、`STATE_BACK_IDLE` 等目标完整版状态。它们目前不代表已经实现，只作为后续扩展方向：

- `STATE_ALARM`：等 AI 行人检测为真，并且报警硬件型号、GPIO、驱动方式确认后再接入。
- `STATE_UPLOAD`：等 P4/C6 联网链路、JPEG 获取和 HTTP 上传路线明确后再接入。
- `STATE_BACK_IDLE`：当前由 `STATE_COOLDOWN` 后回到 `STATE_WAIT_RADAR` 承担类似收尾作用。

## 已经接触到的知识点

- `app_main()` 是 ESP-IDF 应用入口，不再是裸机里的 `main()` 无限循环。
- FreeRTOS 任务可以看成长期运行的执行单元，当前状态机任务用来等待雷达事件并推进检测流程。
- GPIO 中断里不做复杂工作，只通知任务。
- `ulTaskNotifyTake()` / `vTaskNotifyGiveFromISR()` 可以形成一个很小的 ISR 到任务闭环。
- 雷达这类存在检测模块通常可以理解为“有人时保持高电平，无人后变低”，PIR 则通常有几秒级的触发保持时间。
- 当前状态机用冷却状态处理“雷达一直高电平时，上升沿中断不会重复产生”的实际情况。
- `ESP_RETURN_ON_ERROR()` 用来让初始化失败时直接返回错误，避免继续运行到不可靠状态。
- ESP-IDF 组件通过 `idf_component_register()` 声明源文件、头文件目录和依赖组件。
- IDF Component Manager 通过 `idf_component.yml` 下载第三方组件；CMake 里的 `REQUIRES` 依赖的是组件名，不是简单的文件夹路径。
- DSI 屏幕初始化里常见的对象包括 DSI bus、DBI IO、DPI panel / panel handle、frame buffer。
- `#define xxx(arg)` 是带参数宏，`\` 用来把宏定义续到下一行；驱动组件常用这种方式生成结构体初始化模板。

## 当前 vision 组件状态

当前 `vision_init()` 做的事情：

```text
申请 MIPI PHY LDO
    -> 创建 MIPI DSI bus
    -> 创建 MIPI DBI IO
    -> 创建 JD9365 panel
    -> reset / init / display on
    -> 从 DPI panel 获取 frame buffer
    -> 初始化 ESP-DL pedestrian_detect 模型
    -> 初始化 OV5647 sensor
    -> 创建 CSI 控制器
    -> 创建 ISP 处理器
    -> 创建 AI 任务和显示合成任务
```

当前还没有做的事情：

```text
真实硬件运行验证
    -> 根据串口日志修正 OV5647 / CSI / ISP / PPA / ESP-DL 配置
    -> 把 AI 检测结果接入报警和上传
```

这意味着：摄像头到屏幕显示、ESP-DL 行人检测适配层已经进入工程；但还没有记录用户本地编译、烧录后的真实硬件日志和屏幕结果。

当前 vision 目标链路：

```text
sensor -> CSI -> ISP -> PSRAM buffer -> DSI -> LCD panel
```

## Vision 实现与调试约束

实现时遵守：

- 优先使用 ESP-IDF 官方组件、官方例程、Waveshare 组件、Waveshare 例程、ESP Component Registry 中已有组件。
- 不编造未确认的硬件事实、引脚、时序、颜色格式、lane 配置、panel 初始化命令或 ISP 参数。
- API 暴露保持简洁，没必要的不拆成独立 API。
- 简短逻辑没必要包装成函数时，不包装成函数。
- 不为了“能跑”写一大段学生看不懂、难维护的代码。
- 第一版 vision 代码可以保守拼出完整链路，但要预期它需要根据实际日志继续修。

读串口日志时先分类：

| 类别 | 关注点 |
|---|---|
| 启动和重启 | 复位原因、bootloader、panic、Guru Meditation、看门狗、反复重启 |
| 组件初始化 | CSI、ISP、LCD、DSI、I2C、GPIO、PSRAM、DMA、frame buffer |
| 配置不匹配 | 分辨率、颜色格式、lane 数、pixel clock、buffer 数量、panel 输入格式 |
| 数据流状态 | frame done、buffer acquire/release、VSYNC、DMA underrun、timeout |
| 普通噪声 | 与当前问题无关的版本信息、重复状态信息、已知正常打印 |

对有信息的日志，要说明：

1. 这行日志携带了什么信息。
2. 它大概率由哪个组件或源码位置打印。
3. 它和当前现象之间有什么关系。

常见现象处理边界：

- 显示屏亮灭交替、串口显示不断重启时，优先判断是否是 LCD/DSI/panel 配置导致崩溃或反复初始化。
- 显示屏能显示但方向错误时，优先查 Waveshare 或 ESP-IDF 是否已有横竖屏配置、旋转、mirror、swap_xy、panel gap 或 LVGL port 方案，不先手写大段图像旋转代码。
- 颜色错误时，先讲清 RAW、RGB565、RGB888、Bayer pattern、byte order、endian、stride、line buffer、ISP 输出格式、LCD 输入格式之间的关系，再继续改代码。

## 已处理的 ESP-IDF v6.0.1 兼容问题

微雪 JD9365 组件当前版本与 ESP-IDF v6.0.1 存在 API 字段差异，已做学习阶段的本地兼容补丁：

| 文件 | 旧写法 | 当前修正 |
|---|---|---|
| `esp_lcd_jd9365_10_1.c` | `panel_dev_config->color_space` | `panel_dev_config->rgb_ele_order` |
| `esp_lcd_jd9365_10_1.h` | `.pixel_format = px_format` | `.in_color_format = px_format` 和 `.out_color_format = px_format` |
| `esp_lcd_jd9365_10_1.h` | `.flags.use_dma2d = true` | 删除，当前 IDF 的结构体没有该字段 |
| `components/vision/vision.c` | `LCD_COLOR_PIXEL_FORMAT_RGB565` | `LCD_COLOR_FMT_RGB565` |

注意：补丁打在 `managed_components` 里，后续如果刷新依赖、删除 managed components 或升级组件，这些本地修改可能被覆盖。学习阶段可以先这样推进；工程稳定后再考虑 fork、锁版本或把组件转为本地组件。

## 已知问题与风险

| 问题 | 影响 | 当前处理方式 |
|---|---|---|
| 当前开发板不是最新版 ESP32-P4 | 新版资料、例程或 Kconfig 可能和当前板子不完全一致 | 按 `sdkconfig.defaults` 中的 rev v1.x / rev < v3.0 前提判断 |
| 当前雷达 GPIO15、PIR GPIO16 与 P4-C6 SDIO_D1/SDIO_D2 冲突 | 后续 Wi-Fi 会受影响 | 先作为 GPIO 学习代码理解，接入 C6 联网前必须换引脚 |
| 传感器实际接线未最终确认 | 可能导致代码引脚和硬件不一致 | 后续先画出接线表，再改 GPIO |
| DSI 屏幕目前只是编译通过 | 可能仍有运行时显示、供电、时序或方向问题 | 下一步硬件运行时观察日志和屏幕 |
| JD9365 组件补丁位于 `managed_components` | 依赖刷新后可能丢失 | 学习阶段先记录，稳定后再处理组件来源 |
| 摄像头 API 路线存在坑 | 直接用旧接口可能卡死或和 IDF v6 不匹配 | 优先研究官方 `mipi_isp_dsi` 例程和 `esp-video-components` / V4L2 路线 |
| `gpio_install_isr_service(0)` 只能全局安装一次 | 多个模块都安装 ISR service 时可能返回已安装错误 | 后续有多个中断模块时统一管理，或专门处理 `ESP_ERR_INVALID_STATE` |
| AM312 模块资料口径不完全一致 | 供电和输出电平需要确认 | 接入前用实测电压确认 GPIO 输入安全 |
| 摄像头是否无 IR-CUT 尚未最终确认 | 夜间红外条件下的偏色和画质判断可能不同 | 先完成主链路，不提前做夜间效果优化 |

最小下一步：不要跳到 AI，也不要先做报警。先把 OV5647 摄像头管线接进 `vision` 组件，让摄像头图像能进入 ESP32-P4，并尝试复用当前 JD9365 的 frame buffer 做屏幕显示。
